# Evidence Model Review: Integrity, Provenance, Reproducibility (T-007)

**Date:** 2026-07-26
**Review scope:** Spec "Trust Model — Three Layers" and Design §5.1 (Rust Trust Core), §6.1 (IPC Contract)
**Verdict:** ✅ Integrity and provenance achievable in v0.1. Reproducibility deferred to v0.5 with clear architectural path. No overpromise.

---

## 1. Evidence Model Recap

Pactyra's evidence model provides three independently useful layers:

| Layer               | What It Guarantees                                             | What It Does NOT Guarantee                         |
| ------------------- | -------------------------------------------------------------- | -------------------------------------------------- |
| **Integrity**       | Content hasn't changed since registration (hash-chained)       | That the original capture was accurate or complete |
| **Provenance**      | Who, when, where, with what tool, and under what authorization | That the operator's methodology was correct        |
| **Reproducibility** | Another authorized operator can repeat the validation          | That the target will respond identically           |

---

## 2. Integrity Layer — v0.1 Assessment

### 2.1 Architectural Support

The integrity layer is implemented by `pactyra-chain` (Rust):

- **Hash chain structure:** Each receipt contains `parent_hash = SHA-256(previous_receipt)`. The genesis receipt's `parent_hash` is the `scope_hash`.
- **Ed25519 signing:** Every receipt is signed with the operator's Ed25519 key at creation time.
- **Append-only:** The chain only supports append operations. No delete, update, or insert.
- **Verification:** `VerifyChain` walks the entire chain, checks every hash link, and verifies every signature against the public key.

### 2.2 What v0.1 Can Prove

Given a receipt in the chain:

1. The receipt content has not been modified since it was created (hash chain integrity).
2. The receipt was signed by the key that activated the scope (Ed25519 signature verification).
3. Any tampering with any prior receipt would break the hash chain and be detectable.

### 2.3 What v0.1 Cannot Prove (Honest Boundaries)

1. **Original capture accuracy.** If the operator manipulated the target environment before running a tool, the receipt faithfully records the manipulated state. Integrity proves the receipt wasn't tampered with _after creation_, not that the target was in a pristine state.
2. **Completeness of capture.** If the Nmap scan missed a port due to a network issue, the receipt records what Nmap reported — not what actually exists on the target.
3. **Operator identity in the real-world sense.** The receipt proves the action was performed by someone with access to the signing key. It does not prove _which human_ that was. If the operator shares their key, provenance is diluted.

### 2.4 Verdict on Integrity

**Achievable in v0.1.** The hash chain + Ed25519 signing architecture is well-understood, implementable with standard Rust crypto libraries (`ed25519-dalek`, `sha2`), and verifiable with standard tools. No v0.5+ dependencies.

## 3. Provenance Layer — v0.1 Assessment

### 3.1 Architectural Support

The provenance layer is encoded in the receipt schema (design §6.1, `RecordReceipt` IPC operation). Each receipt captures:

| Field           | Source                                  | Recorded When                         |
| --------------- | --------------------------------------- | ------------------------------------- |
| `action_type`   | IPC operation type                      | At Rust handler dispatch              |
| `parameters`    | IPC request payload                     | At ValidateInvocation / RecordReceipt |
| `output_hash`   | SHA-256 of tool stdout+stderr           | After tool execution                  |
| `timestamp`     | System clock (Rust process)             | At receipt creation                   |
| `operator`      | Engagement metadata (set at activation) | At scope activation                   |
| `scope_hash`    | Active scope reference                  | At every receipt creation             |
| `invocation_id` | Generated by Rust at ValidateInvocation | At validation                         |
| `tool`          | IPC request (tool name + version)       | At RecordReceipt                      |
| `authorization` | Permission level (O0–O3 for v0.1)       | At scope activation / expansion       |

### 3.2 What v0.1 Can Prove

1. **Who performed the action:** The operator identity bound at scope activation.
2. **When it occurred:** Timestamp from the Rust process (note: system clock, not a trusted timestamp).
3. **Against which target:** The validated target from ValidateInvocation.
4. **With which tool:** The tool name and version from the invocation.
5. **Under which authorization:** The permission level and scope_hash.

### 3.3 What v0.1 Cannot Prove (Honest Boundaries)

1. **Methodology correctness.** Provenance records _what_ was done, not whether it was the _right thing_ to do. An operator scanning port 80 when port 443 was the actual attack surface would have valid provenance for an incomplete methodology.
2. **Clock accuracy.** The timestamp comes from the system clock of the machine running `pactyra-core`. It can be manipulated by changing the system clock before starting the engagement. Trusted timestamping (NTP-synced, TPM-backed) is a v0.5+ concern.
3. **Operator identity binding.** The operator field is set at scope activation. If multiple humans share the same machine/session, all receipts will show the same operator. Per-human identity (separate keys per operator) is a v0.5 multi-operator feature.

### 3.4 Verdict on Provenance

**Achievable in v0.1.** The receipt schema captures all required provenance fields. The architectural limitation is not in the data model but in the operational environment (system clock, key sharing). These are documented honestly.

## 4. Reproducibility Layer — v0.5 Assessment

### 4.1 Current Architectural Support (v0.1)

The receipt already captures the data needed for future reproducibility:

- Exact tool and version
- Exact parameters (as validated by Scope Guardian)
- Exact target (as validated by Scope Guardian)
- Output hash (for comparison after replay)

### 4.2 What v0.1 Deliberately Defers

1. **Evidence replay engine.** v0.1 does not include a "replay these receipts against this target" capability. The data is there; the execution engine is not.
2. **Diff comparison.** v0.1 does not compare original vs. retest results. It just exports the chain.
3. **Procedure documentation.** v0.1 exports receipts as machine-readable data. Human-readable procedure documentation (step-by-step methodology) is a v0.5 feature.
4. **Environmental preconditions.** v0.1 does not capture what the target environment looked like before the test (OS version, patch level, running services beyond what was scanned). This context is necessary for true reproducibility.

### 4.3 Architectural Path to v0.5

The v0.1 architecture enables reproducibility without redesign:

1. The receipt chain already records exact invocations.
2. The retest engine (v0.5) reads the chain, extracts tool invocations, and replays them through the Worker Manager.
3. New receipts are generated and compared against originals.
4. The diff report shows: what was fixed, what persists, what's new.

No v0.1 data model change is needed. The receipt schema is forward-compatible.

### 4.4 Verdict on Reproducibility

**Correctly deferred to v0.5.** The v0.1 architecture captures the necessary data. The execution engine (replay, diff, environmental context) is explicitly scoped to v0.5. This is architecturally honest — the spec and design do not claim reproducibility in v0.1.

## 5. Overpromise Audit

Each claim in the spec's trust model was checked against the design's architecture.

| Claim                                                                                                     | Architectural Support                              | Overpromise?                          |
| --------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------- |
| "Content hasn't changed since registration"                                                               | Hash chain + Ed25519 signatures                    | No — standard cryptographic integrity |
| "Tampering with any prior receipt MUST be detectable via hash chain breakage"                             | SHA-256 chain, verify on read                      | No                                    |
| "Verification MUST be possible without trusting the platform"                                             | Standalone `pactyra verify` with public key        | No                                    |
| "The integrity guarantee MUST NOT extend to claims about whether the original capture was accurate"       | Explicitly stated as non-guarantee                 | No — honest boundary                  |
| "Who performed the action, when, against which target, with which tool, under which authorization"        | Receipt schema captures all fields                 | No                                    |
| "The provenance guarantee MUST NOT extend to claims about whether the operator's methodology was correct" | Explicitly stated as non-guarantee                 | No — honest boundary                  |
| "The procedure MUST be sufficiently detailed to repeat the validation"                                    | Deferred to v0.5                                   | No — spec says v0.5+                  |
| "The reproducibility guarantee MUST NOT extend to claims that the target will respond identically"        | Explicitly stated as non-guarantee                 | No — honest boundary                  |
| "MUST NOT use language implying 'absolute proof'"                                                         | Spec uses "verifiable," not "proven" or "absolute" | No                                    |

## 6. Recommendations for SDD-007 (Evidence & Receipts)

1. **Receipt schema versioning.** Include a `schema_version` field in every receipt so the format can evolve without breaking v0.1 exports.
2. **Timestamp precision.** Use RFC 3339 with sub-second precision. Document that the timestamp is system-clock-based and not trusted.
3. **Output hash algorithm.** Document that output_hash uses SHA-256. Consider including the hash algorithm in the receipt metadata for future algorithm agility.
4. **Chain export format.** JSONL (one JSON receipt per line) is a good choice for v0.1 — human-readable, line-by-line verifiable, appendable. Consider a binary format for v0.5 if chain sizes grow beyond thousands of receipts.
5. **Standalone verifier robustness.** The `pactyra verify` command should gracefully handle: missing files, malformed JSON, truncated chain, wrong public key, and receipts with future schema versions.

---

## Verdict

**Integrity and provenance are achievable in v0.1 with the current architecture.** The hash chain + Ed25519 signing model is cryptographically sound and implementable with standard Rust libraries.

**Reproducibility is correctly deferred to v0.5.** The v0.1 receipt schema captures the necessary data. The execution engine is a v0.5 concern.

**No overpromise detected.** Every claim in the spec's trust model is accompanied by an honest statement of what the layer does NOT guarantee. The architecture supports the claims that are made.
